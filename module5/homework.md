## Task 1 (Simple): The Staging Gateway & Microservice Fail-Fast Policy

You are tasked with securing a staging application host that will run internal services alongside administrative access. The security and backend architecture teams have established strict perimeter requirements that you must translate into active firewall configurations.

### Starting State:
Your firewall is currently inactive and unconfigured following class cleanup.

### Scenario Requirements:

1. **Firewall Initialization & Telemetry Baseline:**
   - Verify that the `ufw` package is installed on the host.
   - Configure the firewall logging level to `medium` so that rejected and dropped connection attempts generate structured kernel telemetry in `systemd-journald`.

2. **Default Ingress & Egress Posture:**
   - Configure the baseline security posture to silently drop all unsolicited incoming connections (`deny`).
   - Configure the baseline security posture to permit all system-initiated outbound connections (`allow`).

3. **Restricted Administrative Access & Host Gateway Discovery:**
   - The security team mandates that administrative SSH access (port `22/tcp`) must be authorized exclusively from the engineer's host workstation and protected by stateful connection rate limiting.
   - Because virtual guest IP addresses differ from the hypervisor switch address, inspect the kernel routing table to determine the IPv4 address of your host hypervisor default gateway.
   - Add a rate-limited firewall rule authorizing incoming TCP traffic on port 22 originating strictly from that host gateway IP.

4. **Architectural Policy Implementation: Stealth Drop vs. Fail-Fast Reject:**
   Translate these two architectural requirements into the appropriate firewall rule actions:
   - **Requirement A (Perimeter Obfuscation — Port `9443/tcp`):** A legacy administrative interface operates on port `9443/tcp`. Security policy requires that unauthorized external probes targeting this port must receive zero response from the kernel. The host must act as a black hole, forcing external scanners to stall and time out.
   - **Requirement B (Microservice Fail-Fast — Port `5000/tcp`):** An internal mock RPC service operates on port `5000/tcp`. Backend engineering requires that unauthorized or offline requests fail immediately (0 ms) with an active TCP reset (`RST`). This prevents internal microservices from stalling worker threads and exhausting application connection pools.
   - Evaluate whether `deny` or `reject` satisfies Requirement A, and whether `deny` or `reject` satisfies Requirement B. Formulate and execute the corresponding firewall rules.

5. **Firewall Activation & Ruleset Audit:**
   - Enable UFW and confirm that the firewall starts automatically across system reboots.
   - Verify that rules are loaded and default policies are active using verbose and numbered status queries.

6. **External Verification & Kernel Telemetry Deconstruction:**
   - Determine your Linux guest IP address using the appropriate network command.
   - From your **external host machine** (Windows PowerShell/CMD or macOS Terminal), execute a `curl` request to port `9443` with a 3-second connection timeout (`--connect-timeout 3`). Record the client behavior and error code.
   - From your **external host machine**, execute a `curl` request to port `5000` with a 3-second connection timeout (`--connect-timeout 3`). Record the client behavior and error code.
   - In your Linux terminal, query the kernel journal for the `[UFW BLOCK]` telemetry generated by your probe against port `9443`. Extract the single-line log record.

### Deliverables for Task 1:
1. Terminal console output of `sudo ufw status verbose`.
2. Terminal console output of `sudo ufw status numbered`.
3. Side-by-side comparison of the host curl commands and outputs for port `9443` vs. port `5000`, including observed connection timing and curl error codes.
4. An engineering justification (2–3 sentences) explaining why Requirement A required `deny` while Requirement B required `reject`.
5. One extracted raw `[UFW BLOCK]` log record from `journalctl -k` for the port 9443 probe, accompanied by a table mapping `SRC`, `DST`, `PROTO`, `SPT`, and `DPT` to their architectural meanings.

## Task 2 (Medium): Compliance Wiretap, "Black-Box" Outage Triage & Priority Blacklist

You are on call for a web infrastructure environment. You will activate the web tier, capture and audit raw traffic at the packet level to assess unencrypted payload security, triage a sudden simulated web outage using the 5-stage Outside-In sequence, and rectify a failed firewall configuration where an attacker IP bypassed an administrator's blacklist rule.

### Starting State:
Your firewall is active with the rules configured in Task 1. Nginx is installed but currently stopped and disabled from post-class cleanup.

### Scenario Requirements:

1. **Web Tier Provisioning & Baseline Reachability:**
   - Start the Nginx web daemon and configure it to start automatically on boot.
   - Authorize inbound HTTP web traffic on port `80/tcp` in UFW.
   - Verify that Nginx is actively listening on port 80 across all interfaces using the appropriate socket inspection utility.
   - From your external host workstation, verify web reachability by requesting HTTP headers (`curl -I http://<linux_guest_ip>:80`), confirming that the response returns `HTTP/1.1 200 OK`.

2. **Compliance Wiretap & Offline PCAP Forensics:**
   - The security compliance team requires a packet capture audit of unencrypted web traffic to verify whether sensitive headers are exposed on the wire.
   - Launch a bounded packet capture using `tcpdump` that records raw binary packets to `/tmp/compliance_audit.pcap`.
   - Configure your capture to sniff across all network interfaces, exit automatically after capturing exactly 8 packets, and apply a Berkeley Packet Filter (BPF) expression that matches port 80 traffic while strictly excluding administrative SSH (port 22) to prevent terminal feedback loops.
   - From your external host workstation, send an HTTP request containing a custom audit header:
     ```powershell
     curl.exe -H "X-DevOps-Audit: Compliance-Check-5" http://<linux_guest_ip>:80
     ```
   - Once the capture file is recorded, inspect it **offline** using `tcpdump -r`:
     - Apply an offline BPF filter to display only packets where the TCP `SYN` control bit is set (`tcp[tcpflags] & tcp-syn != 0`).
     - Re-read the capture file decoding payloads in ASCII text (`-A`) to verify that the custom audit header and HTTP request body were transmitted in plaintext on the wire.

3. **The "Black-Box" Simulated Outage & Outside-In Diagnostic Triage:**
   - Execute the following staging command on your Linux server to simulate an unexpected production outage without printing internal error details:
     ```bash
     bash -c 'sudo ufw delete --force $(sudo ufw status numbered | grep -E "80/tcp.*ALLOW" | head -n1 | cut -d"[" -f2 | cut -d"]" -f1) >/dev/null 2>&1'
     ```
   - **Incident Alert:** An automated synthetic monitor reports: *"Critical: Public HTTP endpoint is completely unreachable from external networks!"*
   - Without guessing the failure cause or restarting services prematurely, execute the 5-stage **Outside-In** diagnostic methodology to isolate and remediate the incident:
     - **Stage 1 (External Client Test):** From your host workstation, run a client probe with a 3-second timeout (`curl.exe -I --connect-timeout 3 http://<linux_guest_ip>:80`). Note whether the error is a timeout or connection refusal, and document what this indicates.
     - **Stage 2 (Perimeter Verification):** Inside Linux, inspect the active numbered ruleset and query the kernel journal for recent drop events. Record your findings.
     - **Stage 3 (Socket & Process Inspection):** Inside Linux, inspect active listening sockets and query systemd service status for Nginx. Document whether the process and socket are healthy.
     - **Stage 4 (Service Forensics):** Inside Linux, inspect the Nginx service journal logs and validate configuration file syntax.
     - **Stage 5 (Remediation & Validation):** Apply the necessary corrective action to restore traffic, and re-test from your external host to confirm `HTTP/1.1 200 OK`.

4. **Failed Remediation Triage & Emergency Priority Blacklist (`ufw insert 1`):**
   - **Incident Report:** Security monitoring flagged an automated scanner originating from external IP `203.0.113.88` attempting path traversal attacks against port 80. A junior administrator attempted to mitigate the threat by executing:
     ```bash
     sudo ufw deny from 203.0.113.88 to any
     ```
   - **The Problem:** The monitoring dashboard reports that requests from `203.0.113.88` are **still successfully connecting to Nginx on port 80**!
   - **Diagnostic Analysis:** Inspect your active ruleset with `sudo ufw status numbered`. Explain in 2–3 sentences why the junior administrator's deny rule failed to block the attacker from accessing port 80, referencing Netfilter's First-Match evaluation principle.
   - **Priority Remediation:**
     - Delete the ineffective deny rule from the bottom of the chain.
     - Formulate and execute a command that injects the deny rule at **Rule Position 1** so that traffic from `203.0.113.88` is evaluated and dropped before any permissive allow rules.
     - Verify with `sudo ufw status numbered` that the blacklist rule occupies index `[ 1 ]`.
